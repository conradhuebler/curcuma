# CLAUDE.md - Curcuma Development Guide

## Overview

**Curcuma** is a molecular modelling and simulation toolkit for computational chemistry, force fields, and quantum calculations.

**Educational Purpose**: Teaching and research platform prioritizing pedagogical clarity over complex software engineering. Goal: learn, understand, and implement computational chemistry methods without getting lost in C++ abstractions.

## Very General Instructions for AI Coding

## AI-Generated Content and Validation Policy

### Status Labels — Definitions
These labels are used throughout CLAUDE.md files and documentation. Only the human operator may assign ✅ TESTED or ✅ APPROVED.

| Label | Meaning | Who sets it |
|-------|---------|-------------|
| 🤖 AI-generated | Code written by AI, not reviewed by human | AI |
| ⚙️ Machine-tested | Passes automated tests (CI, ctest) | AI |
| 👁️ Human-reviewed | Human has read and understood the code | Human only |
| ✅ TESTED | Human has run it on real problems and it behaves correctly | **Human only** |
| ✅ APPROVED | Human confirms correctness, ready for production | **Human only** |

**The AI must never write ✅ TESTED or ✅ APPROVED on its own work.**

### Conservative Self-Assessment Rules for AI
When documenting implemented features, the AI must apply these rules:

1. **Automated tests pass ≠ correct** — tests only cover what was anticipated. Unknown failure modes exist.
2. **Agreement with reference on test molecules ≠ general correctness** — the reference comparison is only as broad as the test set.
3. **No gaps visible ≠ no gaps exist** — absence of a known bug is not the same as correctness. Especially for AI-generated scientific code: the most dangerous bugs are those that produce plausible but wrong results.
4. **"Implemented" means the code compiles and runs** — it does not imply physical correctness, numerical stability across all inputs, or completeness relative to the reference method.
5. **When in doubt, add a caveat** — a caveat that turns out to be unnecessary is harmless. A missing caveat on wrong code causes user errors.

### Required Documentation for New AI-Generated Features
Every new method or capability added by AI must include in its CLAUDE.md:
- What was tested (which molecules, which conditions)
- What was **not** tested (system classes, edge cases, conditions)
- What is **not implemented** relative to the reference method
- A note that human production testing is pending until the human removes it

### Implementation Standards

#### Educational-First Design Principles
- **Core functionality visibility**: Always provide clear, direct access to the computational chemistry implementation
- **Minimal abstraction layers**: Avoid unnecessary templates, inheritance hierarchies, or design patterns that obscure the scientific content
- **Algorithm transparency**: The actual mathematical/physical implementation should be easily locatable and readable
- **Documentation focus**: Emphasize *what* the code does scientifically, not just *how* it's structured
- **Learning-oriented comments**: Include references to equations, papers, and theoretical background in code comments
- **Method implementation clarity**: Each computational method should have a clear entry point with minimal indirection
- **Accuracy:** 100 % with respect to referenz implementation for any scientific method

#### Code Organization for Learning
- **Flat over hierarchical**: Prefer simple, direct implementations over complex class hierarchies
- **Self-contained modules**: Each computational method should be understandable without deep knowledge of the entire system
- **Clear naming**: Function and variable names should reflect their scientific meaning
- **Minimal templates**: Only use templates when absolutely necessary; prefer explicit types for clarity
- **Direct implementations**: Avoid hiding core algorithms behind layers of abstractions

#### Standard Development Practices
- Mark new functions as "Claude Generated" for traceability
- Document new functions briefly (doxygen ready) with scientific context
- Document existing undocumented functions if appearing regularly (briefly and doxygen ready)
- Remove TODO Hashtags and text if done and approved
- Implement comprehensive error handling and logging
- Maintain backward compatibility where possible
- **Always check and consider instructions blocks** in relevant CLAUDE.md files before implementing
- Reformulate and clarify task and vision entries if not already marked as CLAUDE formatted
- In case of compiler warning for deprecated functions, replace the old function call with the new one
- Implement timing analysis for complex functions
- Keep track of significant improvements in AIChangelog.md, one line per fact
- **Complex Architecture Documentation**: Factory patterns, dispatchers, and multi-step workflows require comprehensive inline documentation following ARCHITECTURE_DOCUMENTATION.md standards
- **BMT output compatibility (MANDATORY)**: Every capability that writes output files MUST route them through `outputPath()` (CurcumaMethod subclasses) or `BMTUtils::outputPath()` (standalone handlers). Hardcoded CWD paths are not permitted. Verify with `-no_bmt` (legacy) and default BMT mode before merging.
- **No UTF symbols in terminal output**: Do not use Unicode box-drawing characters, emoji, arrows (->), checkmarks, or any non-ASCII symbols in fmt::print/std::cout output. Use plain ASCII only. Reason: breaks output in many terminal emulators, log files, and remote shells. CurcumaLogger colored output is exempt (uses ANSI codes, not Unicode).

#### Parameter Definition Standards (MANDATORY for new capabilities)
- **ALL new capabilities MUST use Parameter Registry System** - no static JSON configurations
- **Definition Location**: Define parameters in capability header using PARAM macros within `BEGIN_PARAMETER_DEFINITION(module)` block
- **Naming Convention**: Use **snake_case** exclusively (`max_iterations`, not `MaxIterations` or `maxIterations`)
- **Include Required**: Add `#include "src/core/parameter_macros.h"` to capability header
- **Help Text**: Provide comprehensive, user-facing descriptions for each parameter
- **Categories**: Group parameters logically (Basic, Algorithm, Output, Advanced)
- **Aliases**: Add old parameter names as aliases for backward compatibility during migration
- **Type Safety**: Use correct ParamType (String, Int, Double, Bool) matching C++ type
- **Constructor**: Use `ParameterRegistry::getInstance().getDefaultJson("module")` instead of static JSON
- **Build Verification**: Run `make GenerateParams` and check for validation warnings
- **Documentation**: See reference implementation in `src/capabilities/analysis.h`
- **Migration Guide**: Follow [docs/PARAMETER_MIGRATION_GUIDE.md](docs/PARAMETER_MIGRATION_GUIDE.md) for existing capabilities

## Current Capabilities

### 1. Quantum Mechanical Methods

#### Native Implementations (Educational, No External Dependencies)

> **Default method is `gfnff` for every capability** (`-sp`, `-opt`, `-md`, `-hessian`,
> `-confsearch`, `-casino`): it is the **fast** general-purpose choice. **`gfn2` is the
> accurate one** — native GFN2-xTB, ~100x slower, but with electronic structure. `uff`
> remains available but is no longer any capability's default (Sep 2026). The one place
> `uff` stays the default is `ForceFieldGenerator`'s own `method` parameter, which selects
> which *force field* the FF engine builds (uff | uff-d3 | qmdff | cg) — GFN-FF does not
> go through that class, and its `ff_type = 4` branch there is dead code since the legacy
> `ForceField` GFN-FF path was removed.

> ⚠️ **All native QM methods are AI-implemented and machine-tested only — not human production tested.**
> Results should be validated against external references (TBLite, Ulysses, XTB) before use in research.

## Architecture

### Core Components

#### Energy Calculator (`src/core/energycalculator.h/cpp`)
**COMPLETELY REFACTORED (January 2025)** - New unified polymorphic architecture:

##### **New Architecture**
- **Polymorphic Design**: Single `ComputationalMethod` interface for all QM/MM methods
- **MethodFactory**: Priority-based method resolution with hierarchical fallbacks
- **Unified Interface**: `calculateEnergy()`, `getGradient()`, consistent API across all methods
- **Method Priority System**: `gfn2`/`gfn1` → Native xTB (AP3); `ipea1` → TBLite; `ugfn2` → Ulysses
- **Thread-Safe**: Full multi-threading support maintained
- **Universal Verbosity**: Consistent output control across all computational methods

##### **Method Resolution (New)**
```cpp
// New MethodFactory system (replaces old SwitchMethod)
std::unique_ptr<ComputationalMethod> method = 
    MethodFactory::createMethod("gfn2", config);
double energy = method->calculateEnergy();
```

##### **Supported Method Hierarchies** (AP3, April 2026)
- **gfn1/gfn2**: Native curcuma xTB (canonical); `ipea1`/`ugfn2` for other providers
- **xtb-gfn1/xtb-gfn2**: External GFN — TBLite (USE_TBLITE) → XTB binary (USE_XTB), like `xtb-gfnff`
- **tblite-gfn1/tblite-gfn2**: TBLite explicitly (forces that backend)
- **eht**: Native only (always available, no dependencies)
- **pm3**: Native only (H, C, N, O supported, no dependencies)
- **uff/qmdff**: ForceField wrapper with parameter generation
- **gfnff**: Native C++ GFN-FF (always available, ✅ **COMPLETE**)
- **xtb-gfnff**: Fortran/XTB GFN-FF — ExternalGFNFF (USE_GFNFF) → XTB (USE_XTB)

Only nitrogen has overlapping conditions; the `else if` form is correct for B/C/O/F/S/Cl. Clean check: **nitrobenzene −2.82982873 → −2.83730279 Eh**, matching pprcht (−2.83730275) *and* xtb (−2.83730277). S30L-CI 3/4/5 (benzofurazan guests): +6.91/+4.95/+4.92 → 0.0000 kcal.
    - **(b) Triple-bond torsion (sTors): the reference evaluates only its LAST entry, m times.** `gfnff_engrad.F90:494-503` loops `do i=1,m` but calls `sTors_eg(m, n, ...)`, and `sTors_eg` reads `topo%sTorsl(:,m)` — the array SIZE, not the loop index. Both pprcht **and xtb 6.7.1** therefore drop every entry but the last (and give exactly 0 when the last slot was never filled). Proven on S30L-CI 7/B (alkyne-linked C40H20 macrocycle): the 5 detected quartets match the reference exactly, curcuma's sum 6.125186e-4 Eh equals the observed difference, and `5 x E(entry 5)` = 0 equals the reference's contribution; on 7/A the same model reproduces the *opposite*-signed 8 x E(entry 8). curcuma keeps the correct summation as the default — `erefhalf` is a DLPNO-CCSD(T) diphenylacetylene value, not a fitted parameter — and reproduces the reference bit-for-bit under the new opt-in `-gfnff.storsion_reference_loop_bug true`.     - **(c) The N-outer torsion `fkl` halving used heuristics instead of the reference's pi array — 0.17 kcal/mol.** `gfnff_ini.f90:1693-1694` halves `fkl` when an outer torsion atom is a nitrogen with `piadr==0`. For the lookup itself that fold is value-preserving (row/column 0 and 3 of `bsmat` are identical), which is why it survived so long — but the special cases keyed on the folded value then saw hydrogen (Fortran `hyb=0`) as sp3. An **sp2-N–H** bond therefore matched `hybi==3 && hybj==2 && N` and got `bstrength = 1.24*1.04 = 1.2896` instead of `bsmat(2,0) = 1.0792`, ratio 1.19497 — exactly the measured force-constant ratio. 26. **GFN1: the halogen-bond correction was a stub returning 0.0 — FIXED (Sep 2026, AI/machine-tested)**: `XTB::calcHalogenBondEnergy()` (`xtb_h0.cpp`) read *"The full xTB XB correction depends on charge densities (ρ). For now return 0 — to be implemented if accuracy requires it."* Both halves of that are wrong: the term is **purely geometric** (no density enters), and accuracy did require it. GFN1 — unlike GFN2, which has no such term — carries a classical three-body B–X···A correction over halogen donors X ∈ {Cl, Br, I, At} and Lewis-base acceptors A ∈ {N, O, P, S}, worth up to 0.019 Eh on a 13-atom molecule.
    - **Diagnosis**: the whole gfn1 GMTKN55 residual was this one term. 41 of 2462 structures were above 0.1 kcal/mol and **every single one was in `HAL59`**; no other subset had anything above 0.011. That is the signature of a missing term rather than an accumulating error, and it points straight at the only halogen-specific piece of GFN1.
    - **The term** (Grimme, Bannwarth, Shushkov, JCTC 13 (2017) 1989): `E_XB = Σ_{X,A} f_ang · c_X · (t¹² − k·t⁶)/(1 + t¹²)` with `t = r0/R_AX`, `r0 = radScale·(rad_X + rad_A)` (Mantina/Truhlar atomic radii, radScale 1.3), `k = 0.44`, and `f_ang = (½ − ¼cos θ_BXA)⁶` where **B is the atom nearest to X**, not its bonded partner by any topology rule. Ported verbatim from `external/xtb/src/xtb/halogen.f90` (`xbpot`) plus its triple list in `scf_module.F90:370-404`; `external/tblite/src/tblite/classical/halogen.f90` was compared line by line and is algebraically identical, so the two references do not split here. The analytic gradient came with it and is added in **both** `calculateGradient()` and `calculateGradientGpu()` (the device kernels cover sections 1/2/3 only).
    - **The parameters were already there and unused**: `gfn1_params.hpp` has `halogen_bond` / `halogen_radscale` / `halogen_damping` from the generator. Only **Br (0.0381742), I (0.0321944) and At (0.022)** are nonzero — Cl is in the donor set but its GFN1 bond strength is exactly 0, which is why no chlorine structure ever showed the gap.

MOR41 gfn1: 94/95 structures within **0.006 kcal** of xtb.
    - **Gradient validation**: against xtb's own gradient on `FI_pyr`, max component difference **2.6e-7 Eh/Bohr** — that residual is the pre-existing GFN1 D3 finite-difference term, not the new one. Full-SCF finite differences agree to ≤5e-4 relative and shrink with the step, i.e. FD truncation.

27. **GFN1: the last 4th-period residual is an xtb-vs-tblite STO-6G split, not a curcuma bug (Sep 2026, AI/machine-tested)**: after #26 the gfn1 GMTKN55 residual was max 0.011 kcal/mol, and correlating it with composition made it sharp — **every** main-group 4th-period element present in the set is affected (K, Ca, Ge, As, Se, Br, Kr; 31 of 38 Br structures), while H/C/N/O only appear as their molecular partners. 3rd and 5th period are clean.

28. **Gradients: two unit bugs, found by the first set-wide gradient validation (Sep 2026, AI/machine-tested)**: energies had been validated over thousands of structures for years while gradients were only spot-checked — three small molecules in `ctest` plus ad-hoc finite differences. Building that missing sweep (`scripts/gradient_compare.py`) surfaced two defects immediately, both unit errors, neither affecting a single energy.
    - **(a) GFN-FF returned its gradient in the wrong unit — MD forces were a factor 1.89 too small.** The `ComputationalMethod::getGradient()` contract is **Eh/Angstrom**: native xTB converts explicitly (`xtb_native.cpp:1480`, `m_gradient /= au`), `SimpleMD` feeds the matrix straight into a Verlet integrator whose coordinates are Angstrom, and the finite-difference Hessian differences it against Angstrom displacements. `GFNFFComputationalMethod::getGradient()` passed `m_gfnff->Gradient()` through raw, and GFN-FF works internally in Bohr like its Fortran reference. **Diagnosis by NVE energy conservation**, which separates the two candidate causes cleanly: an integration error shrinks as dt², a force/energy inconsistency does not. GFN-FF drifted **3.4e-3 Eh on CH4 over 500 fs at dt = 0.5, 0.25 and 0.125 fs alike** (ratios 1.00), where gfn2 on the same system drifted 7.7e-5 / 2.2e-5 / 6.0e-6 (ratios 3.5, 3.7 ≈ 4). After the fix GFN-FF gives 7.6e-5 / 1.9e-5 / 5.0e-6 (ratios 4.0, 3.8) — same conservation quality as gfn2.
    - **Why no test caught it**: `gfnff_numgrad_builtin` compares GFN-FF's **internal** `GFNFF::Gradient()` against an **internal** finite difference — both in Bohr, so it is blind to the interface contract. Nothing tested the contract itself.
    - **(b) Every vibrational frequency was too high, for every method.** `Hessian::ConvertHessian()` consumed a Hessian assembled as `(G(x+d) − G(x−d))/2d` from Angstrom coordinates — i.e. Eh/Ang² — as though it were Eh/Bohr², and an empirical **`+ 47.349 cm⁻¹`** offset in the frequency lambda masked part of the error. Measured on H2O against xtb 6.7.1 before the fix: **gfn1 2863.8/6690.5/6890.8 and gfn2 3023.4/6635.5/6636.8** (a factor 1/au = 1.8897 too high), **gfnff 2290.7/5044.2/5047.9** (a factor sqrt(1/au) = 1.3747 — one of the two Angstrom/Bohr factors cancelled for GFN-FF *because of* bug (a); the two did **not** fully cancel). With the `au²` conversion added and the offset removed, all three land within **0.13 %** of xtb (gfnff 0.01 %): gfn1 1490.4/3515.4/3621.4 vs 1490.57/3515.28/3626.07; gfn2 1574.9/3486.3/3487.0 vs 1574.99/3486.05/3491.64; gfnff 1631.9/3635.0/3637.6 vs 1632.01/3634.77/3637.31. That the same two corrections bring **all three methods** onto an external reference simultaneously is the validation of both.
    - **Blast radius**: energies untouched; optimised geometries untouched (a uniform gradient scale does not move a stationary point, though it changes when a gradient-norm convergence test fires); GFN-FF **MD, ConfSearch exploration, and every frequency/thermochemistry number** were affected. No consumer compensated for the old convention — `curcumaopt`, the LBFGS interfaces, `simplemd` and `hessian.cpp` all take `Gradient()` raw — so there is no double correction anywhere.
    - **New regression test** `gradient_unit_contract` (`test_cases/check_gradient_units.py`): (1) analytic gradient vs central FD of the energy with **Angstrom** displacements, for gfn1/gfn2/gfnff — catches any Bohr/Angstrom mix-up at the interface; (2) frequencies vs committed xtb 6.7.1 values (no xtb needed at run time). Verified to **fail on a pre-fix binary**: gfnff gradient ratio 0.5287 = au, frequencies 92 % / 92 % / 40 % high.
    - **One test legitimately changed**: `cli_simplemd_14_gfnff_react_h_recombination` (4 free H atoms, spherical wall, react topology mode) went 3000 K → **6000 K**. Its recombination at 3000 K was an artefact of the too-weak forces letting the atoms approach far closer than the potential allows — with correct forces it fires for **no seed** at 3000 K (five tried) but gives 3 formations / 6 rebuilds at 6000 K and 4/8 at 9000 K/r=1.8. The factor is the expected one: a 1.89× stiffer potential needs ~1.89× the temperature for the same configurations, and 3000 × 1.8897 = 5670 K.
    - **Set-wide result** ([docs/GRADIENT_VALIDATION.md](docs/GRADIENT_VALIDATION.md)): over all 2462 GMTKN55 geometries the median `max|g_cur - g_xtb|` is **3.0e-07 (gfn1) / 4.3e-07 (gfn2) / 3.7e-08 (gfnff)** Eh/Bohr, with 86 / 80 / 76 % of structures at or below 1e-6 — but the distribution is bimodal and a minority disagree by up to 5e-2, so every large one was arbitrated. **For gfnff both codes reproduce the finite difference of their OWN energy exactly** (`AL2X6/al2me6`, `MB16-43/35`, `INV24/NCl3_TS`), i.e. the deviation is the documented pprcht-vs-xtb *energy* split of Known Issues #21/#22, not a gradient defect. For gfn1/gfn2 the picture is different: Those were **arbitrated with finite differences of each program's own energy** (`scripts/gradient_arbitrate.py`) on five independent structures (`ACONF/B_G`, `ACONF/H_ttt`, `WCPT18/ts6`, `BH76/hcnts`, `PNICO23/2`): in every case curcuma's analytic gradient reproduces the FD of **both** codes' energies to six digits while xtb's does not, and the two codes' energies agree. 29. **GFN2: the SCF convergence criterion ignored the multipole moments its own mixer was already mixing — FIXED (Sep 2026, AI/machine-tested)**: found by FD-checking **every** gfn1/gfn2 gradient outlier of the GMTKN55 sweep (202 structures deviating from xtb by >1e-4 Eh/Bohr) against the finite difference of curcuma's **own** energy, instead of extrapolating from the five that had been arbitrated by hand. 14 failed, all of them **H2 or H2+ with gfn2** — analytic 0.033049 against 0.021152 Eh/Bohr, 60 % off on the simplest molecule there is, while the energy still matched xtb to 1e-8.
    - **Not a formula bug.** The built-in `CURCUMA_MP_GRAD_AUDIT` showed the multipole gradient reproducing a frozen-density FD to 1e-10, and the multipole *energy* is exact (curcuma 0.01652010 Eh = xtb's anisotropic ES 0.00781633 + anisotropic XC 0.00870376). Two probes then broke it open: `-scf_threshold 1e-9` gives the correct gradient, and adding a **spectator atom 20 A away** — physically inert — also fixes it. So it is a code path, and it depends on how the SCF terminates.
    - **Root cause.** `checkConvergence_impl` tested `max|dq_shell|` and the energy change only, while `packSCC()` — the vector curcuma's Broyden mixer actually mixes — is `[q_sh, dp_at, qp_at]` for GFN2. tblite converges on `econverged .and. pconverged` with `pconverged = mixer%get_error() < pconv` (`xtb/singlepoint.f90:254-256`), i.e. on the **full mixed vector**. H2 is the extreme case: symmetry pins its shell charges to zero from the first iteration, so `dq` is ~1e-7 immediately and the SCF exits after **2** cycles with the atomic multipole moments still moving. At a density that is off by dP the energy is still right to O(dP^2) — hence 1e-8 agreement — but the gradient only to O(dP). The correlation is exact: H2/gfn2 default is the only case in the probe set that converges in 2 iterations, and the only wrong one (He2 4, H3+ 5, N2 5, HeH+ 7, H2O 8 — all correct).
    - **Fix**: measure the residual on the same vector the mixer works on, `packSCC() - x_in`. `packSCC()` returns `q_sh` for GFN1, so **GFN1 is bit-identical by construction** (verified: its gradient sweep reproduces the previous run exactly, same 56 structures above 1e-3 and the same worst list).
    - **Result**: H2 gfn2 0.033049 -> **0.021144** against xtb's 0.021145 and an FD of 0.021152. GMTKN55 gfn2 gradients: mean 2.24e-04 -> **1.68e-04**, structures within 1e-6 of xtb 79.7 -> **82.6 %**. Energies are untouched (gfn1 MAD 0.000/max 0.011, gfn2 0.000/0.017, unchanged to the print precision) — as expected for a second-order-accurate quantity. `ctest`: the same four pre-existing failures.
    - **Port status for gfn1/gfn2 energy + gradient after this.** Re-running the FD self-consistency check over all 188 remaining outliers: **0 failures**, worst relative deviation 3.4e-03 (FD truncation). So curcuma's analytic gradient is a correct derivative of curcuma's own energy everywhere in GMTKN55, and the energies match xtb. What remains against **xtb's** gradients is the xtb-side inconsistency of Known Issue #28 (geometries with atoms at exactly equal Cartesian coordinates).
    - **The gfn2 energy residual is accumulation, not a term error.** Binned by size over 2458 structures: 1-10 atoms (n=1249) and 11-25 (n=874) are **exactly 0.0000** kcal/mol; 26-50 (n=285) mean 0.00004 / max 0.004; 51-100 (n=50) mean 0.0016 / max 0.017. 30. **GFN2: the last energy residual is the D4 three-body cutoff — an xtb-vs-tblite split, identified and made switchable (Sep 2026, AI/machine-tested)**: Known Issue #29 left the gfn2 energy deviation against xtb characterised ("size accumulation, exactly 0.0000 kcal/mol up to 25 atoms, max 0.017 at 51-100") but not attributed to a term. A term diff does attribute it, completely.
    - **It is the D4 dispersion, and nothing else.** On `ISOL24/i4p` (81 atoms) the repulsion matches to the printed digit and xtb's SCC-minus-dispersion equals curcuma's `Electronic` to **6.6e-8 Eh**, while the dispersion differs by **2.663e-5 Eh** — exactly the total deviation. Across a size sample the same holds: `d_elec` never exceeds 8e-8, `d_disp` carries everything.
    - **The trigger is spatial extent, not atom count.** Every affected structure extends past ~25 Bohr (`ISOL24/i2p` 32.3, `UPU23/0a` 27.7, `ISOL24/i4p` 51.7, `IDISP/F22l` 54.4); every unaffected one stays under 18 Bohr — including 36-atom `DC13/omcb`. An n-alkane series makes the switch-on explicit: C4 (11.4 Bohr) and C8 (21.0) agree to 4e-9, C12 (30.5) jumps to 2.3e-6 and it grows monotonically to 3.5e-5 at C32 (78.4 Bohr).
    - **Cause**: xtb calls `d4_gradient(..., 60.0_wp, 40.0_wp, ...)` (`scf_module.F90:766-767`) — two-body 60, three-body 40 Bohr, D4 CN 40 — while tblite sets `realspace_cutoff(disp3=25.0, disp2=50.0)` (`disp/d4.f90:82`) with CN 30. curcuma had tblite's 50/25/30. Isolating them one at a time shows the **three-body (ATM) cutoff carries 100 % of it**: pair 60 + CN 40 with ATM still at 25 leaves `ISOL24/i4p` at +0.01666 against the original +0.01667, i.e. the two-body and CN cutoffs are accuracy-neutral. With ATM at 40 it drops to **-0.00003 kcal/mol**, and GMTKN55 gfn2 goes from max 0.017 to **MAD 0.000 / max 0.000 over all 2458 structures**.
    - **Decision (operator, Sep 2026): tblite's 25.0 stays the default.** curcuma's GFN1/GFN2 reference is tblite — every parameter table was verified against it and all 16 `sqm_reference` 1e-8 gates are tblite JSONs, two of which (`triose` 9.7e-10 -> 4.9e-6 Eh, `complex` 7.3e-8 -> 5.0e-5) would break at 40. The wider cutoff also costs **~45 % of gfn2 runtime** on a 231-atom system (`complex` energy+gradient 1.08 -> 1.55 s). **`-xtb.d4_atm_cutoff 40.0`** reproduces the xtb binary exactly for anyone comparing against it.
    - **So the remaining gfn2-vs-xtb energy deviation is fully explained and is a reference split, not a port error** — the same situation as the STO-6G 4s/4p split of Known Issue #27, and with the same resolution shape (tblite default, xtb opt-in).
    - **Method note, twice over**: (a) the first attempt at this fix measured "no change at all" because `make` had not picked up a changed default argument in a header — the same trap as Known Issue #15; forcing a rebuild of the dependent translation units revealed the effect immediately. Verify that a rebuild actually happened before believing a null result. (b) The size binning in #29 said "accumulation" and was true but not useful; the term diff took one command and gave the answer. Bin to find the pattern, term-diff to find the cause.
